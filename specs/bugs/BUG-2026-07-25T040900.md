# BUG-2026-07-25T040900: big-release does not update VERSION file

## Problem

big-release creates GitHub releases and git tags but does **not** update the
`VERSION` file. The app reads `VERSION` at request time (main.go `os.ReadFile`),
so the site footer always shows the initial version (`v0.1.0`) regardless of
how many releases are cut.

- **Actual:** Site footer always shows `v0.1.0` even after v0.2.0 was released
  and deployed.
- **Expected:** After a release, the VERSION file should contain the new version
  number, and the site footer should reflect it.
- **Reproduce:** Push a `feat` or `fix` commit to main → CI runs → big-release
  cuts a new version → deploy runs → visit site → footer still shows old version.

## Root Cause Analysis

big-release's `git` plugin commits changes back to the repo. The `changelog`
plugin updates `CHANGELOG.md`. But **no plugin updates the `VERSION` file**.
The commit `3ccc901` (for v0.2.0) shows:
```
CHANGELOG.md | 6 ++++++
```
Only the changelog file was modified. The VERSION file was left untouched.

### First attempt: exec plugin (reverted)

big-release has an `exec` plugin that runs shell commands during the plugin
lifecycle. Initial fix tried adding it to `.big-release.yml`:

```yaml
plugins:
  - changelog
  - git
  - github
  - exec

exec:
  prepareCmd: |
    echo "${nextRelease.version}" > VERSION
```

**Result:** Failed with `plugin "exec" verify conditions failed: exec publisher
not configured or not enabled`.

**Root cause investigation:** The exec plugin reads its config from
`ctx.Config.Publishers["exec"]` (verified in `internal/plugins/exec.go` line
52), NOT from the plugins section. It requires a `publishers.exec` block:

```yaml
publishers:
  exec:
    enabled: true
    options:
      commands: |
        echo "${nextRelease.version}" > VERSION
```

However, even with correct config, the exec plugin's `Prepare` runs BEFORE the
git plugin's `Publish` (which creates the git tag), so the tag wouldn't exist
yet for the version to be finalized. This timing issue makes the exec plugin
unsuitable for post-tag VERSION file updates.

## TDD Fix Plan

No new tests needed — existing test suite verifies the app renders VERSION
file content. The fix is validated by deploying and checking the live site.

1. **FIX**: Add `Update VERSION file` step to `test-build-release.yml` after
   `Run big-release`. The step reads the latest git tag (just created by
   big-release), strips the `v` prefix, writes it to `VERSION`, commits with
   `[skip ci]`, and pushes.
   **verify:** `grep -q 'Update VERSION file' .github/workflows/test-build-release.yml`

2. **VERIFY DEPLOY:** Push to main → CI runs → big-release cuts a version →
   VERSION gets committed → site shows new version.
   **verify:** `gh run list --limit 2 --json conclusion -q '.[].conclusion' | grep -q success`

## Acceptance Criteria

- [ ] Workflow has a step after big-release that updates VERSION from the tag
- [ ] The commit uses `[skip ci]` to avoid re-triggering the pipeline
- [ ] A new push produces a release that updates the VERSION file
- [ ] The live site footer shows the new version

## Resolution

**Approach:** Workflow step (not exec plugin). Added `id: big-release` to the
"Run big-release" step, then a new "Update VERSION file" step that:
1. Reads latest tag via `git describe --tags --abbrev=0`
2. Strips `v` prefix
3. Skips if VERSION file already matches
4. Writes to VERSION, commits with `[skip ci]`, pushes

`.big-release.yml` remains at 3 plugins (changelog, git, github) — no exec.
